# 多 Agent 協同分派

當單一上下文面臨海量文件注意力稀釋、跨專案路徑與狀態污染，或缺乏對抗視角導致決策盲區時，依規範評估並調度多個專職 Agent 協同完成任務。強調嚴格啟動門檻、自包含派工簡報、以程式碼為事實錨點，以及任務結束後的生命週期清理。

## 1. 工作模式

| 模式 | 觸發條件 | 執行方式 |
| --- | --- | --- |
| 說明 | 詢問多 Agent 調度原則、拓撲選型或簡報寫法 | 解釋適用場景與門檻；不派發任何子 Agent，不更動專案 |
| 定向處理 | 明確的多文檔分析、跨雙專案邊界核對或單一架構議題對抗討論；預設模式 | 評估門檻後選擇合適拓撲，分派最小必要數量的專職 Worker，收斂成果後結束 |
| 範圍審查 | 複雜跨系統重構、多庫全面依賴盤點或大規模需求探索 | 先列出系統邊界、拓撲架構與角色分工清單，分批次派工、交叉反證並產出整合報告 |

**輸入**：目標文件集合、跨專案路徑、需求議題或對抗命題；預期交付深度與驗證標準。

**調度單位**：`目標領域／專案邊界 + 專職角色 + 派工簡報 (Briefing) + 證據產物`。已知上下文能解答者不重問；只有涉及核心架構裁決或不可逆操作時才向使用者確認。

## 2. 按需讀取細節

- 啟動門檻、派工簡報契約、防循環與資源回收：按需讀 [PROCEDURE.md](references/PROCEDURE.md)。
  - 門檻評估與防濫用反模式：見第 1 節。
  - 派工簡報 (Briefing) 五要素與隔離規範：見第 2 節。
  - 工具適配（Subagent / Swarm / Workflow）：見第 3 節。
  - 反證檢驗與爭端仲裁：見第 4 節。
  - 生命週期與清理：見第 5 節。
- 具體拓撲架構與協同協定：按需讀 [TOPOLOGIES.md](references/TOPOLOGIES.md)。
  - 拓撲一：海量文件平行分讀與萃取（Parallel Fan-Out & Reduce）。
  - 拓撲二：跨專案／多 Repo 隔離探勘（Cross-Project Specialists）。
  - 拓撲三：需求研擬與對抗審查（Adversarial Debate & Review）。
- 需交付多 Agent 規劃紀錄、跨專案邊界矩陣或共識收斂報告時：讀 [REPORTING.md](references/REPORTING.md)。

各 skill 可獨立使用，無隱含依賴；未達啟動門檻時維持單一 Agent 執行，不強制調度子 Agent。

## 3. 標準流程

1. **門檻判定**：核對任務特性（文件量、跨專案正交性、對抗審查需求）。若單一上下文可順暢完成，堅決不開子 Agent；確認需開時，限制 Worker 數量（通常 2–3 個）。
2. **拓撲選型**：依任務性質選擇對應拓撲（平行分讀、跨專案隔離、對抗辯論），明確定義主調度者（Coordinator）與各 Worker 之角色邊界。
3. **派工與簡報**：為每個 Worker 撰寫自包含的「派工簡報 (Briefing)」——包含目標、路徑白名單、工作空間隔離模式（`inherit` / `share` / `branch`）、證據規範與輸出 Schema。
4. **平行執行與隔離**：Worker 獨立運行於各自上下文，專注於限定領域，嚴禁越界讀寫；主調度者監控進度，不進行無效輪詢。
5. **收斂、仲裁與清理**：主調度者收集各 Worker 之結構化產物，進行交叉反證與事實比對；解決衝突後立即回收/終止 Worker（如 `swarm kill`），交付最終整合報告與未決事項。

## 4. 派工、證據與隔離規則

- **不為開而開**：子 Agent 有通訊延遲與上下文重複成本。單檔修改、局部除錯、簡單字串搜尋一律單 Agent 搞定。
- **冷啟動原則**：子 Agent / Swarm Worker 啟動時沒有主對話歷史。派工簡報必須自給自足，清楚交代背景、依賴檔案路徑與明確產出格式。
- **邊界隔離**：跨專案分析時，Worker 僅限於分配之專案目錄；有檔案寫入需求時必須使用獨立分支或工作區（`share` / `branch`），避免 Git 狀態衝突。
- **事實錨定**：Agent 討論嚴禁「憑空腦補」或「互相客套」。所有觀點、反駁與結論必須附帶實際程式碼路徑、行號、Commit、RFC 段落或實測結果。
- **反證優先**：對抗審查中，Challenger 必須主動尋找能推翻 Proposer 假設的實作邊界、安全隱患或效能瓶頸；反證成立即修正方案。
- **輪次硬限制**：討論與辯論以 2–3 輪為限，嚴防無限複讀。無法達成共識時，提煉為 Trade-off 矩陣交由使用者裁決。

## 5. 交付與完成條件

- 交付物包含：各 Worker 之核心發現、跨專案/跨領域交叉比對結論、對抗討論後確認之需求/架構規格，以及仍待確認的具體問題清單。
- 生命週期已完成回收：所有暫存 Worker 已確認終止（Killed / Done），暫存分支或臨時檔案已清理或合併，無懸空運行的背景進程。
- 若任務中斷、Worker 遭遇權限不足或依賴缺失，如實記錄阻塞點與已完成片段，不以虛構推論偽裝為已驗證共識。
