# 多 Agent 協同分派作業規範

依需求按需讀取以下章節，不需每次通讀。
索引：門檻與反模式、派工簡報契約、工具適配、反證與仲裁、生命週期回收。

---

## 1. 啟動門檻與反模式

啟動子 Agent 會帶來顯著的上下文複製成本、通訊延遲與整合開銷。必須遵守以下硬性門檻：

### 1.1 嚴禁啟動多 Agent 的情境（反模式）

| 禁忌情境 | 原因 | 正確做法 |
| --- | --- | --- |
| 單一檔案／函數之修改或除錯 | 局部上下文即可容納，派發只會增加傳遞耗損 | 主 Agent 直接利用編輯工具完成 |
| 線性順序強依賴的任務 | 後續步驟需等前一步驟執行結果，無法並行 | 依序在主對話中逐步驗證執行 |
| 1–2 次字串搜尋即可定位之問題 | 搜尋工具（如 `rg`）耗時毫秒級，開 Agent 延遲數十秒 | 主 Agent 直接執行搜尋指令 |
| 「看起來任務很大」但範疇未明 | 派發只會導致子 Agent 盲目全庫掃描、產出空泛摘要 | 主 Agent 先定位核心入口再決定是否拆解 |
| 純粹追求「展示效果」的多 Agent 漫談 | 無實質資訊增量，嚴重浪費 Token 與對話額度 | 單一 Agent 進行結構化推論 |

### 1.2 建議啟動多 Agent 的觸發條件

符合下列條件之一時，方可評估啟動多 Agent（預設 2–3 個，嚴禁無節制擴張）：

1. **資訊體積超載**：需要通讀多份長篇文件、大型規格書或上萬行歷史 Log，單一對話視窗勢必發生「Lost in the middle」或 Context 飽和。
2. **多專案／多 Repo 邊界隔離**：任務橫跨兩個或多個獨立專案（例如前後端、客戶端與服務端、微服務遷移），需避免檔案路徑混淆、搜尋結果雜湊或 Git 狀態衝突。
3. **對抗性質的需求／架構審查**：面臨重大技術選型、模糊需求規格化或架構重大重構，單一 Agent 容易產生肯定偏誤（Confirmation Bias），需設立 Challenger 角色主動尋找漏洞與反例。
4. **完全正交的獨立探勘**：數個獨立模組需要分別盤點現況，且各自的依賴完全解耦。

## 2. 派工簡報 (Briefing) 契約規範

子 Agent 與 Swarm Worker 具備「冷啟動」特性，預設無法讀取主對話歷史。派工簡報必須是一份自包含的任務契約。

### 2.1 簡報五要素

派工簡報必須明確包含以下五點，缺一不可：

1. **Role（明確角色與定位）**：如 `Auth Spec Analyst`、`Frontend Service Auditor`、`Architecture Challenger`。
2. **Objective（單一具體目標）**：說明本次委派必須回答的核心問題或交付產物，不給模稜兩可的泛指要求。
3. **Scope & Whitelist（路徑與操作白名單）**：
   - 明確標注允許讀取的目錄／檔案路徑（如 `docs/specs/auth/*.md` 或 `backend/api/`）。
   - 聲明操作權限（預設皆為唯讀；需要修改時標註限定檔案）。
4. **Evidence Standard（證據標準）**：
   - 結論必須附帶精確路徑與行號（如 `file:///path/to/file#L12-L30`）。
   - 對於架構推論，必須指出依據之程式碼結構或文件段落；不得將「推測」寫成「事實」。
5. **Output Schema & Stop Condition（產出格式與停止條件）**：
   - 指定回傳格式（如 Markdown 表格、指定 JSON 格式）。
   - 明確停止條件（如「找出 3 個主要衝突點即停止」、「若模組未實作該介面回報 MISSING 後立即返回」）。

### 2.2 工作空間隔離模式選擇

| 模式 | 適用情境 | 注意事項 |
| --- | --- | --- |
| `inherit` | 純讀取任務、分析文件、跨專案唯讀比對；預設模式 | 共享當前目錄，任何檔案寫入皆會直接影響主工作區 |
| `share` | 需要各自執行測試、生成臨時產物，但需共享 git 歷史 | 各 Worker 擁有獨立的 working tree，互不干擾未提交變更 |
| `branch` | 涉及實質程式碼修改實驗、可能失敗的重構探勘 | 建立完全隔離的 git clone/branch，確認方案可行後再由主 Agent 整併 |

## 3. 工具適配與機制選型

依據當前宿主環境具備的工具能力，選擇最合適的多 Agent 機制：

```
                      [任務類型與互動需求]
                               |
        +----------------------+----------------------+
        |                                             |
   [單向批次 / 平行探勘]                      [即時協同 / 對抗討論]
        |                                             |
  [大量獨立項目?]                               [需對話看板?]
    /        \                                     /        \
  (是)       (否)                                (是)       (否)
   |          |                                   |          |
run_workflow invoke_subagent                    swarm    雙 Agent 輪流
(動態腳本調度) (獨立上下文探索)                (Swarm 看板)  invoke_subagent
```

### 3.1 Antigravity 環境機制映射

- **`invoke_subagent`**：
  - 適用：海量文檔獨立分讀、單一專案專題深入調查。
  - 特性：背景非同步運行，回傳訊息主動喚醒主 Agent。**切勿使用 sleep 輪詢**。
- **`swarm`**：
  - 適用：研究討論、需求對抗審查、多專家線上會商。
  - 特性：透過共用訊息看板溝通。主調度者使用 `action: "add"` 派發，以 `@worker` 提及派工；任務收斂後必須執行 `action: "kill"` 終止 Worker。
- **`run_workflow`**：
  - 適用：批次 fan-out（例如盤點 30 個微服務 API、批次檢查 50 份規範文檔）。
  - 特性：以 Python 腳本編排 `parallel()`、`agent()` 與 `pipeline()`。

### 3.2 通用 CLI / 外部 Agent 環境適配

若運行於不具備原生 swarm/workflow 之宿主環境（如標準 CLI）：
- 將多 Agent 流程拆解為「階段化提示詞（Phased Prompting）」。
- 主 Agent 自行切換視角，嚴格隔離不同專案的檢索命令與工作目錄。

## 4. 交叉核驗、反證與爭端仲裁機制

多 Agent 討論的常見陷阱是「彼此客套、互相贊同」或「陷入文字遊戲的無限循環」。必須建立剛性仲裁機制：

### 4.1 事實層級規範

當不同 Agent 的結論產生衝突時，依以下優先級裁決事實：
$$\text{Runtime 執行結果} > \text{測試案例輸出} > \text{實際程式碼實作} > \text{官方/專案文件} > \text{Agent 推論}$$

- 任何 Agent 的宣稱，若與程式碼實際行號不符，視為無效論據。
- 不得以「多數 Agent 投票」取代實際程式碼證據。

### 4.2 對抗辯論收斂規則

在需求探索與架構評審拓撲中：
1. **硬限制輪次**：對抗辯論最多進行 2 輪（Round 1：提案 vs 質疑；Round 2：修改 vs 複核）。
2. **質疑必須具體**：Challenger 提出的質疑必須具備「觸發條件（Trigger）」、「失敗場景（Failure Case）」與「可反證依據（Counter-evidence）」。泛泛而談的「可能會有效能問題」視為無效反對。
3. **不可抗爭端交由使用者**：若涉及業務優先級、成本與效能之固有權衡（Trade-off），停止 Agent 爭辯，提煉為決策表呈報使用者。

## 5. 生命週期管理與資源回收

多 Agent 任務必須維持嚴格的資源生命週期，杜絕殭屍進程與懸空環境：

1. **成果萃取**：Worker 產出結果後，主調度者立即將關鍵結論與證據記錄至主對話或交付檔案中。
2. **即時終止**：
   - Swarm Worker：呼叫 `swarm(action: "kill", name: "<worker>")` 釋放資源。
   - 分支工作區：若 Worker 建立了 `branch` 或 `share` 工作目錄，確認變更已 merge 或放棄後，進行目錄與分支清理。
3. **例外與超時處理**：
   - 若 Worker 在合理預期時間內未回傳或遭遇工具阻礙，主調度者應果斷介入，檢視其 status，必要時 kill 並改由主 Agent 補足關鍵缺口。
   - 記錄「已驗證部分」與「因阻礙未完成部分」，不隱瞞失敗。
