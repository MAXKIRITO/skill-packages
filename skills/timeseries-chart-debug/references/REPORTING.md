# 檢查紀錄與交付格式

適用於使用者要求報告或進行範圍審查；局部修正只需在回覆中保留必要資訊，不為符合格式建立多餘檔案。以下定義本包的檢查紀錄與交付格式。

## 1. 檢查紀錄

記錄目標 repo／模組、來源版本或 dirty 狀態、任務模式、檢查單位、排除範圍、已執行動作與環境。純說明模式不需要取得版本或填表。

覆蓋狀態固定使用：

| 狀態 | 定義 | 必要資料 |
| --- | --- | --- |
| 已檢查 | 該單位已按聲明的方法完成判讀，不代表沒有問題 | 位置、方法、結果 |
| 待驗證 | 特定缺口會影響結論，目前未能完成 | 缺什麼、原因、下一個具體檢查 |
| 未檢查 | 本次尚未處理或超出範圍 | 範圍與原因 |
| 不適用 | 已確認該檢查不適用此單位 | 明確理由，不可用來掩蓋未知 |

同一單位若只讀來源未測 runtime，描述為「已檢查：source；runtime 待驗證」，不能把整列簡化為全數通過。

## 2. 問題紀錄

每個保留的候選記錄：

- 識別：本次穩定的簡短 ID、根因與受影響單位；同根因合併症狀，不同根因分開。
- 預期：來自需求、有效契約、目前程式規則或明示假設，不能只憑個人偏好。
- 證據：repo 相對路徑、符號或必要行號、方法、版本／條件與結果。測試需附實際指令與 outcome；無執行不可補造 log。
- 差異：觸發條件、實際行為及已建立的影響，避免放大到未證明的情境。
- 反證：查過什麼補償機制或不成立條件，以及判讀結果。
- 處置：最小修正／建議、驗證方法、仍需確認的條件。

問題結論使用「已確認」「待判定」「已排除」。已確認仍需標示證據方法，來源能確定的事實不必為形式強迫網路重現；需要 runtime 條件的主張不可只靠來源升級成已觀察結果。

待判定必須有具體候選路徑及關鍵缺口；沒有來源或合理觸發條件的泛泛猜測不列入問題表。已排除保留足夠原因，後續相同來源不重複報問題；版本／條件改變後需重判。

不要為所有候選預設安全嚴重度。按功能正確性、相容性、資料風險、可用性或維護影響排序；未確定的影響要標假設。

## 3. 反證與最後複核

交付前重新讀取支持關鍵結論的目前來源，核對每個指令的真實結果及修正後行為。主動尋找會否定候選的條件，不只重讀自己的摘要。

同一 agent 自我複核可稱「再次核對」，不能稱「獨立審查」。只有已獲授權且實際有其他審查者／agent 驗證時，才說明獨立審查結果；不得因使用本格式就自動啟動代理或擴張任務。

若新證據推翻原結論，更新問題與覆蓋紀錄，不保留前後矛盾的報告。修正後不能只把原重現案例改成符合實作的期待值。

## 4. 報告模板

```text
目標／版本：
模式與範圍：
排除範圍：

檢查單位 | 已查位置 | 方法 | 覆蓋狀態 | 結論／缺口

問題 ID | 預期與差異 | 證據及條件 | 反證結果 | 影響 | 處置

變更：本次實際修改，或只有建議
驗證：實際指令／方法、環境、成功／失敗與證據層級
未完成：缺口、限制與精確下一步
```

少量問題可用段落呈現相同資訊。原始碼、log、payload 與完整翻譯不應大量複製到報告；機密、身份資料及可重用憑證不得保留。

## 5. 結束規則

範圍中有待驗證／未檢查項時，報告必須呈現部分完成狀態。不以「沒有發現」推導整個系統無問題，不把工具結束或格式檢查成功等同於行為驗收。

需要後續工作時提供最小下一步與所需環境；不擅自執行正式變更、不無限擴大搜尋，也不因單一受阻項停止已授權且仍可完成的部分。
