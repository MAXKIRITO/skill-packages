# MQTT 資料流檢查

## 1. 工作模式

| 模式 | 觸發 | 執行方式 |
| --- | --- | --- |
| 說明 | 問方法、規則或概念 | 回答必要部分；無定位需求不掃 repo，不預設改檔或寫報告 |
| 定向處理 | 指定症狀、檔案、diff 或小範圍修改；預設模式 | 走下方流程，只展開本次相關檢查 |
| 範圍審查 | 明確要求檢查模組、介面集合或完整指定範圍 | 先列單位與排除項，再追覆蓋與缺口；完成只指已聲明範圍 |

輸入：環境、裝置／topic、症狀與時間；主動測試另需已授權身份、topic 與界限。

檢查單位：publisher＋topic／filter＋payload 類型＋consumer＋結果。能由上下文確認的資訊不重問；只有會改變判斷或授權的關鍵缺口才詢問，不為填表要求額外資訊。

## 2. 按需讀取細節

詳細規範在 [PROCEDURE.md](references/PROCEDURE.md)。環境與連線見第 1–2 節；topic／consumer／儲存見第 3–4 節；API／UI 見第 5 節；主動測試見第 6 節；交付見第 7 節。

先定位章節再讀必要片段，不預設整份載入，也不自動載入其他 skills。每個 skill 可獨立安裝，沒有 sibling skill 的隱含依賴。

需要範圍審查紀錄或正式報告時，再讀 [REPORTING.md](references/REPORTING.md)：它定義覆蓋狀態、問題欄位、反證、最後複核與報告模板。一般局部修正不需載入。

## 3. 標準流程

1. 界限：用來源與既有證據確認 broker、身份、topic、consumer 及測試範圍，避免輸出秘密與真實敏感 payload。
2. 分段：區分傳輸、登入、訂閱、publish ack，再查 parse／validation／dispatch；每段標示已觀察或僅來源推論。
3. 追蹤：queue／batch → commit → historical／snapshot → API／cache → UI，用同一事件或可辨識小樣本串證據。
4. 驗證候選：查 retained、其他 consumer、重送、晚到與 filter 等反證。執行既有 e2e 前讀副作用；主動測試限專用身份、topic 與少量訊息。
5. 驗收：按症狀測去重、亂序或重連；清理只限本次 fixture 與授權操作。交付最後成功段、第一個缺口、修正與驗證。

## 4. 證據與覆蓋規則

- 遵循專案規則與使用者授權。讀來源、提出方案、執行測試與修改環境是不同動作；載入 skill 不擴張授權，已有授權不重複確認。
- 證據標為 `source`、`test` 或 `runtime`，記錄當前路徑／符號、條件及結果；來源推論不得描述為已執行觀察，舊報告需對目前版本複查。
- 候選問題須有預期、具體差異、影響與來源。確認前查最可能的反證；反證成立即撤回，關鍵事實未定就明列缺什麼及如何驗證。
- 範圍審查用「檢查單位／已查位置／證據方式／結論／待驗證事項」簡表。未查項不能算通過，不適用需理由。局部修正保留必要上下文即可，不強制建立檔案。
- 修改或切版本後重新驗證依賴的證據。測試失敗須區分實作問題、既有失敗與環境限制；格式檢查成功不代表功能全數通過。

## 5. 交付與完成條件

交付範圍、已確認結果、最小修正（若有）、實際驗證與限制。多項問題按根因去重，再依已知影響排序；使用者要求報告時才保存到指定或約定位置。

QoS／PUBACK 不代表 DB commit。不得擅自重用正式 client ID、訂閱 #、發正式控制命令、刪 retained 或大量重送；非預期副作用或到達測試界限即停止。

超出範圍、授權或可用環境時，停止依賴該條件的操作，繼續可完成的工作並給具體下一步。不以更多泛讀、無限重試或跳過失敗來宣稱完成。
