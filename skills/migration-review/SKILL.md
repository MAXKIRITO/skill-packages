# Migration 審查

## 1. 工作模式

| 模式 | 觸發 | 執行方式 |
| --- | --- | --- |
| 說明 | 問方法、規則或概念 | 回答必要部分；無定位需求不掃 repo，不預設改檔或寫報告 |
| 定向處理 | 指定症狀、檔案、diff 或小範圍修改；預設模式 | 走下方流程，只展開本次相關檢查 |
| 範圍審查 | 明確要求檢查模組、介面集合或完整指定範圍 | 先列單位與排除項，再追覆蓋與缺口；完成只指已聲明範圍 |

輸入：migration／schema diff／失敗訊息；engine、版本、runner、基準及目標依專案確認。

檢查單位：migration ID＋操作／表＋相容性階段＋環境假設。能由上下文確認的資訊不重問；只有會改變判斷或授權的關鍵缺口才詢問，不為填表要求額外資訊。

## 2. 按需讀取細節

詳細規範在 [PROCEDURE.md](references/PROCEDURE.md)。基準與 schema 矩陣見第 1–2 節；runner 見第 3 節；部署見第 4 節；驗證與執行方案見第 5–6 節；結論見第 7 節。

先定位章節再讀必要片段，不預設整份載入，也不自動載入其他 skills。每個 skill 可獨立安裝，沒有 sibling skill 的隱含依賴。

需要範圍審查紀錄或正式報告時，再讀 [REPORTING.md](references/REPORTING.md)：它定義覆蓋狀態、問題欄位、反證、最後複核與報告模板。一般局部修正不需載入。

## 3. 標準流程

1. 基準：確認 engine／版本、runner、schema、來源版本與是否含執行；先讀 status／config 的行為，不能假設命令唯讀。
2. 核對：DDL／DML、型別、constraint、舊資料及 model／query／新舊 app 相容性。
3. 追蹤：discovery → transaction → operation → metadata → commit／rollback；確認實際 connection、交易傳播、DDL 限制、重跑與並行控制。
4. 評估：依資料量與部署模式分析鎖、重寫、backfill、expand／contract 及資料回復；查 engine／框架已提供的保障。
5. 驗收：先形成具體方案，在符合授權的隔離 DB 驗證必要案例；實際執行必須匹配已授權目標。分開交付靜態檢查、隔離驗證與指定環境套用結果。

## 4. 證據與覆蓋規則

- 遵循專案規則與使用者授權。讀來源、提出方案、執行測試與修改環境是不同動作；載入 skill 不擴張授權，已有授權不重複確認。
- 證據標為 `source`、`test` 或 `runtime`，記錄當前路徑／符號、條件及結果；來源推論不得描述為已執行觀察，舊報告需對目前版本複查。
- 候選問題須有預期、具體差異、影響與來源。確認前查最可能的反證；反證成立即撤回，關鍵事實未定就明列缺什麼及如何驗證。
- 範圍審查用「檢查單位／已查位置／證據方式／結論／待驗證事項」簡表。未查項不能算通過，不適用需理由。局部修正保留必要上下文即可，不強制建立檔案。
- 修改或切版本後重新驗證依賴的證據。測試失敗須區分實作問題、既有失敗與環境限制；格式檢查成功不代表功能全數通過。

## 5. 交付與完成條件

交付範圍、已確認結果、最小修正（若有）、實際驗證與限制。多項問題按根因去重，再依已知影響排序；使用者要求報告時才保存到指定或約定位置。

審查不自動授權連 DB 或修改。不得任意改已套用 migration、清 metadata 或強制重跑；down／dump 存在不代表資料可還原。未知 pending、基準不符或部分成功時停止依賴操作並回報。

超出範圍、授權或可用環境時，停止依賴該條件的操作，繼續可完成的工作並給具體下一步。不以更多泛讀、無限重試或跳過失敗來宣稱完成。
