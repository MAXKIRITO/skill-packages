# 專案上下文作業規範

索引：範圍與盤點、查證、文件分工、要求分類、增量維護、共用寫法、驗證、案例。只讀本次需要的章節。

## 1. 範圍與文件盤點

先分清使用者要求的是回答、保存摘要、整理固定規則、更新某次變更，還是範圍內文件重整。保存要求應以已明確授權的範圍為限；詢問「這個專案是什麼」本身不代表要改 README。

記錄目標 workspace／repo、讀者、任務範圍、排除項與既有文件位置。多 repo 環境先區分共享服務與各應用；不為完整感一開始列出所有子目錄及依賴。

優先讀作用範圍內的 AGENTS.md 及文件索引，再沿任務入口查找摘要、架構、開發規範、測試與部署文件。已有載入內容且未變更時不重讀。

建立精簡分工表，通常留在上下文即可：

| 資訊 | 現有主要文件 | 本次需要更新 | 證據入口 |
| --- | --- | --- | --- |
| 用途與啟動 | README／既有入門文件 | 依任務判斷 | manifest、啟動入口 |
| 架構與資料流 | 現有 overview／architecture | 受影響模組 | route、service、storage |
| 開發要求 | AGENTS.md／開發指南 | 已明確指定的要求 | 使用者指示、現行規則 |

若現有文件結構已能承載內容，就補充原位置，不另建整套文件。重新命名或搬移文件只在使用者要求或確有必要時進行，並同步入站連結。

## 2. 有限探索與來源查證

### 2.1 初次建立摘要

先從有限入口建立可用地圖：

1. 專案目的與主要讀者／使用者，依明確需求及現有介紹判讀。
2. 主要應用、服務與資料儲存，從 manifest、入口及設定名稱確認。
3. 一條代表性的互動或資料流，追到實際處理與資料來源；其他未追路徑只列入口。
4. 開發、build、測試與啟動指令，核對實際 scripts／工具設定與工作目錄。
5. 與本次範圍相關的限制、固定要求與已知未知。

摘要不是完整 API 清單、資料字典或依賴樹。若無法以代表路徑支持整體說法，縮小聲明，不為完成摘要通讀所有實作。

### 2.2 證據分類

| 類別 | 能支持的敘述 | 不能直接支持 |
| --- | --- | --- |
| 目前來源 | 某入口、scripts、設定或資料流確實存在 | 服務已成功啟動、正式站同樣部署 |
| 已執行驗證 | 指定版本與環境下的實際結果 | 所有環境都成立 |
| 明確要求 | 使用者或作用範圍內規則指定的動作 | 該要求已完成或永遠適用所有 repo |
| 推測／建議 | 需要查證的候選或可選改善 | 既有事實、必須遵守的規則 |

摘要保留相對路徑與符號作來源。需要版本／日期時記錄實際查證時間及來源狀態；不要用更新日期暗示每個段落都已重新驗證。

不得為蒐集資訊讀取或輸出不必要的 secrets、完整環境變數、真實個資或 DB dump。設定只描述必要鍵名、用途與取得方式。

## 3. 文件分工與單一主要來源

以下是可用分工，不是強制檔名：

| 角色 | 內容 | 不重複放入的細節 |
| --- | --- | --- |
| README | 專案用途、最短啟動流程、重要入口 | 完整架構與所有規則 |
| 專案摘要／overview | 模組地圖、技術、主要資料流、指令、限制與來源 | 大段原始碼與所有 endpoint |
| 開發規範 | 依任務或模組劃分的固定要求及驗證方式 | 一次性的任務對話 |
| AGENTS.md | 必要常駐要求、作用範圍與按任務閱讀入口 | 所有參考文件全文 |

沒有既有位置時，可使用 `docs/PROJECT_CONTEXT.md`、`docs/DEVELOPMENT_RULES.md`；已有 overview、development-guidelines 或 `docs/ai/` 時沿用。可以同一檔分節承載，不必為每種角色建檔。

詳細事實與規則各有一個主要維護位置，其他文件以摘要及相對連結導向。必要常駐約束可在 AGENTS.md 保留精簡且語意一致的表述；不得以消除重複為由使約束失效。

閱讀入口應回答「做哪種任務時讀哪份文件」，不能要求每次載入全部背景。人與 AI 都能從 README 或既有索引抵達相同細節。

## 4. 要求分類與可執行寫法

### 4.1 判斷持續性

- 固定要求：使用者明確指示持續遵循，或已存在於有效專案規範。保留適用 repo／目錄、觸發條件及來源。
- 單次條件：此次重現資料、暫時方案、某次測試設定。留在本次交付或指定任務文件，不自動升格為常駐規則。
- 現行慣例：由程式看出的常見做法。可描述為目前實作；除非有規則來源，不能改寫為強制要求。
- 建議：agent 提出的改善。明確標為建議，不用「必須」或綁定未授權流程。
- 未確認：缺少產品、環境或有效範圍資訊。列出具體問題，不猜出一套新規範。

### 4.2 固定規則的最低資訊

每項規則應回答：適用哪裡、何時觸發、要做什麼、如何判定完成、依據是什麼。重要例外有明確來源才記錄，不能自行發明。

可使用規則表：ID、範圍、觸發、要求、驗證、依據／狀態。少量規則也可用可直接理解的句子，不為格式把一句規則拆成長表。

例如「改前端要驗證」應在工具與既有要求已確認後具體寫成「修改指定前端應用時，在該目錄執行已核對的 build 指令；無法完成時交代原因」。不要把某專案的指令寫成所有專案通用要求。

### 4.3 衝突與精簡

先區分文件過期、不同目錄的局部規則、建議與要求，再判斷是否真正衝突。事實衝突以目前有效來源核對；要求衝突須保留原意並指出哪個選擇需要決策，不能悄悄採較寬鬆版本。

精簡 AGENTS.md 時逐項核對舊要求的新位置、作用範圍與可見性。若移至詳細文件，必須保留能使其在相關任務被讀取的明確指引；對每次工作都必須生效的約束，保留精簡常駐表述。

## 5. 增量維護與失效處理

由指定 diff、變更檔案、規則或錯誤文件切入。對應「變更事實／要求 → 主要文件段落 → 入口連結」，只更新受影響部分。

| 變更 | 應核對的位置 |
| --- | --- |
| 入口／目錄／模組重命名 | overview、README／索引及入站連結 |
| API／資料來源／事件流程 | 摘要中的相關資料流與主要來源 |
| build／測試指令 | manifest、相關開發指南、必要常駐要求 |
| 使用者新增固定要求 | 作用範圍、規則主要位置、AGENTS 任務入口 |
| 既有規則撤銷／取代 | 原來源、主要規範、必要常駐表述及相關入口 |

來源版本變更後重新讀受影響段落；不因摘要仍存在就視為最新。更新與來源不一致的舊內容，不能只在末尾追加相反說法。

定義維護觸發條件即可，不自動建立排程、背景索引或每次任務都執行全面掃描。持續規則或過期結論缺來源時，列出待確認，不隨意刪除。

## 6. 人與 AI 共用的寫法

- 用短段落說明用途與原因，再用表格列入口、規則或指令。術語首次出現時用讀者能理解的語句說明。
- 路徑使用 repo 相對形式；連結相對於文件所在目錄。可執行指令註明工作目錄、必要前提與驗證狀態。
- 簡單資料流可用箭頭或 Mermaid，但圖不能取代路徑、關係與必要限制，也不要求安裝渲染工具。
- 不寫「AI 請自行理解」或只有機器可懂的隱含標記；同樣不為人類閱讀另複製一份詳細架構。
- 摘要保留可定位來源，不複製長函式、完整 log、所有依賴或每個檔案內容。人讀得懂脈絡，AI 能按入口選讀。

## 7. 驗證與完成

交付前確認：

1. 描述的模組、路徑、入口與必要符號存在；資料流聲明有來源支持。
2. 指令與目前 scripts／設定相符，工作目錄與前提清楚；未執行就不說可成功啟動。
3. 相對連結可用，既有索引可抵達新內容，沒有新舊規則相互矛盾。
4. 固定要求可追溯、範圍明確，沒有把單次條件或建議當成強制規則。
5. 使用者既有文字及未涉及的區段保留，必要常駐要求沒有因精簡失效。
6. 未確認事實、未查模組與未執行的驗證具體列出；沒有宣稱全專案或正式環境全數驗證。

文件更新可做路徑／連結／來源核對，不為修改 Markdown 執行無關 build。若工具無法解析動態路由或環境設定，標示來源判讀限制，提出最小後續查證。

## 8. 案例

### 已有 `docs/ai/`，希望人也能看

檢查現有 overview、開發指南與索引是否足夠。改善白話介紹、閱讀路徑及來源連結，從 README 提供入口；不因目錄名稱含 AI 另建一份相同的 `PROJECT_CONTEXT.md`。

### 使用者說「這次先不要跑整套測試」

視為單次條件，依任務交代實際驗證及限制，不保存為「所有修改都不用測試」。若明確要求永久改規則，才核對作用範圍與既有規範衝突。

### 摘要寫使用 Redis，程式只留下未啟用設定

查啟動與實際呼叫入口；證據不足時寫「設定存在，使用狀態待確認」，不能僅因依賴安裝便宣稱是主要資料流。

### 精簡長 AGENTS.md

將架構背景導向主要 overview，將條件式細節導向相應開發指南。保留每次必須生效的規則，並核對所有舊要求的覆蓋與優先順序；不是只剩一行「請讀 docs」。
