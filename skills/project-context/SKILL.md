# 專案上下文維護

讓維護者能理解專案並找到實作，讓 AI 能按任務選讀，重用同一份已查證的事實與要求。沿用現有文件的路徑、語言與結構，每項詳細內容只維護一個主要來源。

## 1. 工作模式與授權範圍

| 模式 | 觸發 | 執行方式 |
| --- | --- | --- |
| 說明 | 詢問專案結構、規則或文件安排 | 回答必要摘要；未要求保存時不新增文件 |
| 定向處理 | 更新指定模組、規則、摘要或某次變更影響的文件 | 預設模式，只維護相關段落與入口 |
| 範圍審查 | 明確要求建立專案摘要、整理固定要求或整體文件維護 | 先定義專案邊界、讀者、文件分工與排除項，再完成範圍內文件 |

輸入為目標 workspace／repo、任務目的、已知變更或要保存的要求。先由現有文件與對話確認，不要求使用者重述已知資訊；只有會影響要求的持續性、適用範圍或衝突處置時才詢問。

工作單位是「事實／要求＋所屬模組＋主要文件＋證據來源」。多 repo workspace 應分清共享內容與各 repo 的獨立規則，不假設根目錄就是 Git repo。

## 2. 按需讀取細節

- 初次建立、增量更新、來源判讀與規則整理：按需讀 [PROCEDURE.md](references/PROCEDURE.md) 第 1–5 節。
- 人與 AI 共用寫法、驗證、衝突及案例：讀 PROCEDURE 第 6–8 節。
- 要新增文件、整理需求表或交付文件維護結果時，讀 [REPORTING.md](references/REPORTING.md) 的文件契約與可裁剪範本；不要直接建立範本中的所有檔案。

不依賴其他 skills，也不預設通讀整個 repo 或既有長文件。

## 3. 標準流程

1. **盤點入口**：讀作用範圍內尚未載入的規則、現有 README／文件索引，確認哪些文件已承載摘要與開發要求。保留使用者既有文字與結構。
2. **定向查證**：從 manifest、啟動入口、相關設定與代表資料流驗證本次要描述的事實；只讀必要模組。記錄來源位置、驗證方式與未確認事項。
3. **分配內容**：README 放用途與快速入口；詳細摘要與規則放既有主要文件；AGENTS.md 保留有效的必要常駐要求及明確的按任務閱讀指引。不存在合適位置時才新增文件。
4. **整理與更新**：區分已確認事實、明確固定要求、單次任務條件、建議與未知。固定要求寫清適用範圍、觸發條件、動作及驗證；只改受影響段落，詳細內容以連結共用。
5. **驗證交付**：核對路徑、連結、指令、規則來源與跨文件一致性。交付文件位置、主要更新、實際驗證與缺口；只有實際要求的文件才新增或改寫。

## 4. 文件與證據規則

- 文件面向人與 AI：用清楚標題、白話說明、實際路徑、表格與指令；不建立平行的「人類版」和「AI 版」詳細摘要。
- 已存在的 `docs/ai/`、架構文件、開發指南與索引可直接沿用；名稱含 AI 不代表必須另寫人類副本。
- 檔案／程式證據、已執行驗證與使用者明確要求分開記錄。建議不得寫成必須遵守的規則，慣例不得偽裝為已授權要求。
- 單次 bug 條件或局部測試設定不自動永久保存。要求持續性不明時先保留在本次上下文，繼續其他已明確授權的文件工作。
- 精簡 AGENTS.md 不得悄悄刪除、削弱或擴大既有規則。需要持續生效的約束保留原作用範圍，不能僅移到按需文件後假設每次都會被載入。
- 不因整理文件而執行服務、安裝依賴、變更部署／資料庫、提交或推送。已授權的必要驗證依原任務執行，未執行的命令僅標為來源宣告或待驗證。

## 5. 完成與停止條件

範圍內的摘要與要求已有可追溯來源、主要維護位置及可用入口；讀者能知道系統用途、從何開始、何時套用規則與如何驗證。未知及未覆蓋模組明確列出。

若文件與來源衝突、固定要求互斥或有效範圍無法確定，指出具體衝突，先完成不依賴該決策的部分，不自行創造產品決策。沒有實測時不得宣稱啟動成功、測試通過或部署已驗證；沒有計量時不宣稱固定 token 節省比例。
