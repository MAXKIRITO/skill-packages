# 程式碼探索作業規範

依需求讀取以下章節，不需每次通讀。索引：定位與搜尋、閱讀與追蹤、資訊重用、驗證與停止、紀錄與案例。

## 1. 定位與搜尋

### 1.1 建立任務邊界

先從對話建立：要解決的行為、使用者提供的路徑／符號／錯誤、是否允許修改、驗收條件。能由既有上下文推得的資訊不重問。

指定檔案不是自動授權重構整個模組；要求找位置也不是要求修正。尚未知道 repo 根目錄時，在目前目錄或相關父目錄確認，避免掃使用者家目錄。多 repo workspace 分別記錄受影響 repo。

只有需要比較版本或修改時才讀相關 Git status／diff；不要為純概念提問蒐集 Git 背景。不要讀取與任務無關的秘密檔。

### 1.2 選擇搜尋操作

| 已知線索／所需答案 | 操作 | 下一步 |
| --- | --- | --- |
| 已有檔案與位置 | 讀該區段 | 不再先找同名檔案 |
| 只知檔名或副檔名 | `rg --files <scope> -g '<glob>'` | 讀最相關候選 |
| 字面 endpoint、錯誤或符號 | `rg -n -F -e '<literal>' <scope>` | 看匹配周圍函式 |
| 只要有哪些檔案 | `rg -l -F '<literal>' <scope>` | 避免列出所有匹配行 |
| 只要知道存在與否 | `rg -q -F '<literal>' <scope>` | exit 1 是無匹配，exit 2 是操作錯誤 |
| 符號有同名歧義 | 使用語言伺服器／語法索引（若可用），或加上 import、namespace、路由條件 | 先驗證定義再追 references |

Shell 參數應正確引用；搜尋內容中的 `$()`、反引號或 regex 特殊字元不得意外執行或改變搜尋語意。使用者輸入只作資料。

### 1.3 漸進擴大

順序通常為指定檔案 → 同目錄／已知使用方 → 所屬模組 → 相關子專案 → 必要時跨 repo。每次擴大要能說明原範圍缺哪一段證據。

結果太多時加目錄、glob、精確字串或 import 條件；結果過少時先確認拼字、別名、生成路由、ignore 與動態載入，不直接判定不存在。已知目標在隱藏或忽略路徑中才對該範圍開放搜尋。

不要用完整輸出遭截斷的搜尋支撐「全部」結論。若只有前幾筆，標示候選範圍並縮小查詢。不要以 `head` 截掉後半結果就宣稱查完。

## 2. 閱讀與追蹤

### 2.1 選擇閱讀範圍

先讀匹配位置的函式、class 或設定區塊，再按需要展開 import、呼叫方與被呼叫端。用行號分段讀大檔；切片沒有涵蓋 guard、錯誤處理或生命週期時，繼續補齊再判斷。

已有 README／文件索引時，只讀對應入口及任務需要的連結。沒有文件時從實作確認，不為開始工作先建一套文件架構。

生成碼先追生成來源；問題涉及發行包差異、產物損壞或執行版本時才讀生成結果。lockfile 只在依賴解析／版本問題時展開，不用它推測所有架構。

### 2.2 跨檔案追蹤

每一步回答具體問題：輸入從哪來、在哪轉換、在哪判斷、哪裡產生輸出。相同函式名須核對實際 import；不要把文字匹配當作呼叫關係。

跨端／事件／設定變動，才追直接使用方與必要的邊界；一般局部樣式修正不需要展開資料庫。共用函式的修改則必須找受影響使用方，避免以省閱讀為由忽略相容性。

### 2.3 反證

提出原因後，查最可能推翻它的條件，例如 interceptor 已轉換欄位、guard 已處理、不同實作才是執行入口、舊檔未被引用。不能只找支持原先猜測的匹配。

## 3. 資訊重用

任務期間保留精簡定位表即可，不預設寫入 repo：

| 問題 | 位置／符號 | 已確認行為 | 下一個未知 |
| --- | --- | --- | --- |
| 誰組 query | 路徑與函式 | 使用本地時間字串 | service 是否轉 UTC |

不要貼整段原始碼作為「快取」。使用檔案路徑、符號與少量證據行即可。只有需要量測時記錄工具輸出量、搜尋次數或讀取範圍；未取得實際 token 計量時不得報省了多少 token。

修改檔案、換 branch、外部更新或摘要遺失重要證據後，重讀將依賴的區段。穩定的文件位置可重用，舊行號與舊結論不能直接當作目前事實。

長期索引僅在使用者要求時建立，記錄 repo、來源版本／狀態、相對路徑、用途與更新條件；不要儲存秘密或把所有程式複製進索引。

## 4. 驗證與停止

### 可開始修改的條件

- 已找到實際執行入口，而非只找到名稱相似的檔案。
- 能說明現行行為及本次要求的差異。
- 受影響的共用介面、使用方與必要驗證已確認，或具體列出缺口。

### 可以結束探索的條件

定位問題：已指出實作與必要關係。修改問題：已完成修改及範圍相符的驗證。審查問題：聲明範圍中的項目已有證據或明確未驗證狀態。

遇到依賴缺失或環境不明，繼續能完成的靜態工作，列出哪個事實仍無法判定。不要用無關泛讀取代阻塞處理。

## 5. 紀錄與案例

較大範圍審查可維護「範圍／問題／已讀位置／證據方式／結論／缺口」表；小修正保留在上下文即可。除非使用者要報告，不額外寫探索日誌。

證據方式分 `source`（目前原始碼）、`test`（已執行測試）、`runtime`（已觀察執行結果）。推論須與觀察分開；沒有匹配不等於證明不存在。

### 案例：指定元件的數值顯示錯誤

先讀格式化與 props，再追直接供值位置。若 API 原值正確但格式化丟失小數，只改該轉換並驗證代表值；沒有證據顯示來源錯誤時，不掃描整個後端。

### 案例：搜尋不到字面 URL

先確認 base URL、prefix 與動態組字，找 route name 或 handler；如果 URL 來自生成 client，再查 schema／generator。不能據此直接新增重複 endpoint。

### 交付格式

直接給位置／修改結論、關鍵證據、驗證與剩餘缺口。不要逐條重述每次搜尋，也不要以「已完整理解全專案」結尾。
