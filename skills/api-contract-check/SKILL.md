# API 契約檢查

## 1. 工作模式

| 模式 | 觸發 | 執行方式 |
| --- | --- | --- |
| 說明 | 問方法、規則或概念 | 回答必要部分；無定位需求不掃 repo，不預設改檔或寫報告 |
| 定向處理 | 指定症狀、檔案、diff 或小範圍修改；預設模式 | 走下方流程，只展開本次相關檢查 |
| 範圍審查 | 明確要求檢查模組、介面集合或完整指定範圍 | 先列單位與排除項，再追覆蓋與缺口；完成只指已聲明範圍 |

輸入：endpoint、欄位、串接症狀、diff 或相關檔案；預期行為與可用測試。

檢查單位：method＋route＋版本＋使用方＋契約面。能由上下文確認的資訊不重問；只有會改變判斷或授權的關鍵缺口才詢問，不為填表要求額外資訊。

## 2. 按需讀取細節

詳細規範在 [PROCEDURE.md](references/PROCEDURE.md)。契約矩陣見第 2 節；追蹤與反證見第 3–4 節；修正及測試見第 5 節；交付與案例見第 6 節。

先定位章節再讀必要片段，不預設整份載入，也不自動載入其他 skills。每個 skill 可獨立安裝，沒有 sibling skill 的隱含依賴。

需要範圍審查紀錄或正式報告時，再讀 [REPORTING.md](references/REPORTING.md)：它定義覆蓋狀態、問題欄位、反證、最後複核與報告模板。一般局部修正不需載入。

## 3. 標準流程

1. 定位：確認實際 URL、method、prefix／proxy rewrite、版本與 scope，不能只比較表面字串。
2. 追蹤：client → transport／interceptor → route／middleware → handler／service → serializer → consumer；資料語意需要時才展開 model／migration。
3. 比對：按受影響面核對輸入、auth／tenant context、輸出、錯誤、分頁及 retry／timeout，記錄轉換層與來源位置。
4. 驗證候選：查補償轉換、fallback、版本及權限條件，建立具體觸發與影響；先決定相容策略再修改。
5. 驗收：執行必要的行為與跨端檢查，同步 schema／文件；交付 endpoint、使用方、相容性、修正及實際驗證層級。

## 4. 證據與覆蓋規則

- 遵循專案規則與使用者授權。讀來源、提出方案、執行測試與修改環境是不同動作；載入 skill 不擴張授權，已有授權不重複確認。
- 證據標為 `source`、`test` 或 `runtime`，記錄當前路徑／符號、條件及結果；來源推論不得描述為已執行觀察，舊報告需對目前版本複查。
- 候選問題須有預期、具體差異、影響與來源。確認前查最可能的反證；反證成立即撤回，關鍵事實未定就明列缺什麼及如何驗證。
- 範圍審查用「檢查單位／已查位置／證據方式／結論／待驗證事項」簡表。未查項不能算通過，不適用需理由。局部修正保留必要上下文即可，不強制建立檔案。
- 修改或切版本後重新驗證依賴的證據。測試失敗須區分實作問題、既有失敗與環境限制；格式檢查成功不代表功能全數通過。

## 5. 交付與完成條件

交付範圍、已確認結果、最小修正（若有）、實際驗證與限制。多項問題按根因去重，再依已知影響排序；使用者要求報告時才保存到指定或約定位置。

不把 build 當契約通過、spec 差異當 bug 或前端補 tenant ID 當授權修復。範圍內契約面有證據或明確缺口，且修正相容性與驗證一致才完成。

超出範圍、授權或可用環境時，停止依賴該條件的操作，繼續可完成的工作並給具體下一步。不以更多泛讀、無限重試或跳過失敗來宣稱完成。
