# 三方頭腦互搏協同協定手冊 (Triad Co-Design & Adversarial Debate)

本手冊規範在設計推演過程中，多個 AI Agent（或單 Agent 內部三重思維視角）如何分工協作、互相質疑、頭腦互搏，進而逼出最高品質的設計決策架構。

---

## 1. 核心哲學：為什麼需要「頭腦互搏」？

單一 Agent 在生成設計時往往具備「樂觀主義偏誤」：它總是假設文字長度剛剛好、網路速度飛快、使用者眼力絕佳、一切都在 Default 狀態下完美運作。

為了徹底根除這種 AI 設計幻覺，本協定強制導入**「紅藍軍對抗與總監仲裁」的三元體系（The Triad）**：
- **Lead（領導 / 設計總監）**：主導方向、防發散、定邊界、裁決爭議、收斂產出。
- **Designer（設計家 / 設計架構師）**：主動創新、構建視覺美學、組織 60-30-10 與 OKLCH 配色、推導 8pt 空間與元件解剖學。
- **Critic（審查員 / 易用性與可用性盲點質疑）**：扮演 Devil's Advocate，專門挑刺、模擬邊界災難、抓 a11y 違規與認知負荷陷阱。

---

## 2. 三方角色定義與行為邊界

```
+--------------------------------------------------------------------------+
|                       👑 Lead (設計總監 / 流程主導者)                       |
|  - 掌控雙鑽石發散與收斂節奏                                               |
|  - 定義專案核心 Persona 與 1~2 項最高優先級任務                            |
|  - 主持辯論，記錄未決爭議，依據「使用者利益 > 系統一致性 > 實作成本」裁定  |
|  - 最終交付標準化《設計決策架構書 (Design Spec)》                          |
+--------------------------------------------------------------------------+
                    |                                  ^
                    | (指派任務簡報)                     | (匯報最終收斂結果)
                    v                                  |
+------------------------------------+   對抗辯論   +------------------------------------+
|    🎨 Designer (設計架構師)         | <--------> |      🔍 Critic (審查質疑員)        |
| - 提出具體設計方案與版面構想         | (限 1~2 輪) | - 模擬破壞性邊界情境 (文字爆裂/白屏) |
| - 建立 60-30-10 OKLCH 語意色票     |            | - 查驗 Gestalt 格式塔五原則偏離    |
| - 推導模組化字階與 8pt 空間網格     |            | - 檢驗 Laws of UX (Hick/Fitts)     |
| - 定義元件插槽與 8 大互動狀態       |            | - 揪出遺漏之狀態機與 WCAG 違規     |
+------------------------------------+            +------------------------------------+
```

| 角色標識 | 核心目標 | 嚴格禁止事項 (Forbidden) |
| :--- | :--- | :--- |
| **👑 Lead** | 確保設計做對的事（Do the right thing），掌控節奏與最終收斂。 | 禁止跳過問題定義直接讓 Designer 畫圖；禁止放任討論無限循環（嚴格限制 2~3 輪）。 |
| **🎨 Designer** | 確保把事做好（Do things right），以系統化美學與人本原則推導解法。 | 禁止使用模糊形容詞（如「感覺挺現代」）；禁止在無設計背書下隨機選色或選尺寸。 |
| **🔍 Critic** | 確保不犯致命錯誤（Catch blind spots），揭露邊界狀態與可用性陷阱。 | 禁止發出「我完全贊同」、「這個設計太棒了」等社交客套；禁止提出無法量化或無對應原則的純主觀意見。 |

## 3. 派工簡報契約 (Briefing Contracts)

當使用 Subagents (`invoke_subagent`) 或 Swarm (`swarm add`) 啟動多 Agent 協同，或在單 Agent 模式切換視角時，必須依循以下自包含簡報格式：

### 3.1 派發 Designer 之簡報範本
```markdown
@role: Design-Architect
@workspace: inherit
@objective: 依據 Lead 定義之問題與核心任務，推導完整系統化視覺架構與設計規格。
@context: 
- 目標受眾與情境: [填入 Persona 與使用場景]
- 核心任務 (Core Task): [填入 1~2 件核心行動]
- 內容約束 (Content-First): [填入文案範例與極端長度預估]
@deliverables:
1. 視覺方向與佈局構成 (說明版面結構、視線流動與 0-Card 空間運用)
2. 60-30-10 感知色彩系統 (具體 OKLCH 數值與 M3 語意角色表)
3. 模組化字級比例 (Modular Type Scale 階梯與行寬行高)
4. 8pt/4pt 空間系統 (宏留白 vs 微留白數值)
5. 核心元件解剖插槽與三層 Token 映射
@stop_condition: 輸出完整設計提案草案即停止，等待 Critic 審查反饋。
```

### 3.2 派發 Critic 之簡報範本
```markdown
@role: Usability-and-Accessibility-Critic
@workspace: inherit
@objective: 扮演嚴苛審查員，以認知科學、格式塔原則、Laws of UX、8 狀態矩陣與 WCAG 標準對 Designer 的提案進行全面挑刺與對抗性審查。
@input_proposal: [引用 Designer 產出之設計提案]
@attack_vectors:
1. 格式塔偏離 (是否有無效邊框破壞接近性？視覺焦點是否分散？)
2. 認知負荷 (Hick's 決策選項是否過多？Fitts's 點擊熱區是否足夠？)
3. 色彩與對比 (60-30-10 是否超標？WCAG 對比度是否 < 4.5:1？是否純靠顏色傳達狀態？)
4. 8 大互動狀態完整度 (Default/Hover/Focus-Visible/Active/Disabled/Loading/Error/Empty 是否缺漏？)
5. 內容極端破壞測試 (超長文案折行、網路延遲、空資料引導)
@output_format:
- 質疑必須採用標準批判語法：[情境] + [觸發條件] + [受害影響] + [違反原則] + [修正要求]
@stop_condition: 產出條列化質疑清單即停止，等待 Designer 抗辯或修正。
```

## 4. 對抗辯論三階段協定 (Adversarial Protocol)

```
[階段 1: 總監定調與初版提案]
Lead 確立問題邊界與真實文案
       |
       v
Designer 輸出初版設計提案 (Draft Design Spec)
       |
       v
[階段 2: 紅藍軍對抗審查 (限 1~2 輪頭腦互搏)]
Critic 發動對抗質疑 (Challenges & Edge-case attacks)
       |
       v
Designer 針對質疑進行修正或以設計科學提出抗辯 (Defense / Revision)
       |
       v
Critic 複查修正結果 (Pass 或標記為 unresolved trade-off)
       |
       v
[階段 3: 總監仲裁與合約交付]
Lead 裁定爭端，鎖定最終設計合約，輸出正式《設計決策架構書》
```

### 4.1 對抗質疑標準語法（嚴防口水戰）
Critic 的每一條質疑，必須具備以下五要素結構，否則視為無效質疑：
```markdown
- **【質疑點名稱】**：
  - **情境 (Scenario)**：當使用者處於 [特定狀態，例如：移動中單手操作/弱網環境]
  - **觸發條件 (Trigger)**：當資料出現 [例如：用戶名稱超過 25 個字元 / 查詢無結果]
  - **受害影響 (Impact)**：畫面將出現 [例如：按鈕寬度被撐爆換行 / 頁面死白無引導]
  - **違反原則 (Violated Axiom)**：違反了 [例如：Content-First 原則 / 8 大狀態 Empty 規範 / Fitts's Law]
  - **修正要求 (Actionable Demand)**：建議 Designer 將其修改為 [具體修正方案]
```

### 4.2 Designer 回應與抗辯規範
- **接受修正**：明確更新具體數值、Token 或狀態插槽定義。
- **提出抗辯**：若 Designer 認為 Critic 的要求過度設計或違背了更核心的原則，必須以「認知科學原理」或「使用者心智模型」提出反駁理由，禁止憑個人喜好狡辯。
- **終止閾值（Hard Stop）**：對抗質疑與抗辯以 **2 輪為限**！若第二輪仍未達成共識，雙方立即停止爭辯，將衝突點陳述為 Trade-off，提交 Lead 裁決。

---

## 5. 總監仲裁原則與 Trade-off 決策矩陣

當 Designer 與 Critic 出現分歧時，Lead 依據以下**決策優先級天平**進行裁定：

$$\text{使用者核心任務通暢度} > \text{可讀性與無障礙安全} > \text{視覺美學驚艷度} > \text{實作複雜度}$$

### 裁決記錄範例：
```markdown
### 👑 Lead 仲裁紀錄：
- **爭端議題**：首頁主行動按鈕是否應在預設狀態下使用脈衝發光動畫？
- **Designer 主張**：加入微光脈衝可加強 10% 強調色預算之吸引力，引發使用者好奇心。
- **Critic 質疑**：持續的動畫會分散注意力，增加認知疲勞，且對前庭障礙使用者不友善（違反 a11y 減少動態原則）。
- **Lead 裁定結果**：採納 Critic 質疑。取消預設持續脈衝動畫；改為僅在使用者完成前置表單填寫、可送出瞬間播放一次 400ms 的平滑微高光過渡，兼顧引導與安靜專注。
```

## 6. 單 Agent 模式下的「三重認知沙盒」執行指南

若執行環境為單一對話、無多 Agent 工具可用時，主 Agent 必須在思考與回覆中**顯式分離三重人格**，禁止將發想與審查混成一團糊泥：

```markdown
### 🎯 [Lead 設計總監：問題定義與核心任務]
... (輸出使用者角色、核心任務與內容約束) ...

### 🎨 [Designer 設計架構師：系統美學與方案推演]
... (輸出 60-30-10 OKLCH、模組化字階、8pt 留白、元件插槽) ...

### 🔍 [Critic 審查質疑員：頭腦互搏對抗審查]
... (發動 2~3 項嚴苛質疑：邊界崩潰、8狀態缺漏、對比度不足) ...

### 🎨 [Designer 設計架構師：抗辯與方案修正]
... (修正缺陷，給出更新後的具體參數) ...

### 👑 [Lead 設計總監：仲裁與最終規格藍圖鎖定]
... (輸出最終可交接之 Design Spec) ...
```
這種顯式切換能強迫模型自我反思，發揮出與多 Agent 協同同等的嚴謹審查品質。
